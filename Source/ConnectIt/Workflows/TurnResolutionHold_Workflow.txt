ConnectIt Turn Resolution Hold — Workflow
=============================================

WHAT THIS IS
------------
UTurnBasedParticipantManagerComponent (Plugins/UnrealTurnBasedMechanics/.../Turn/
Participant/TurnBasedParticipantManagerComponent.h/.cpp) used to advance from the
resolution phase (EndTurn) to the next turn on a fixed-duration timer
(TurnResolutionDuration) -- a guess at how long visual/logic work would take, not a
real signal that the work was actually done. That's gone. In its place:
BeginResolutionHold() / EndResolutionHold(), a plain hold counter with zero knowledge
of tags, board state, or ConnectIt at all. AdvanceToNextParticipant only runs once the
count is back to zero.

AConnectIt_BoardManager is what drives the counter, and it does so by combining two
things that are deliberately kept separate:

  1. UConnectIt_BoardSequencerComponent::IsIdle() -- is a board-change visual sequence
     (piece placed / line scored / win / shift) still in flight or queued? This
     component knows nothing about turns; it only exposes this as a board-domain fact.
     See GameEventSubsystem_Workflow.txt.

  2. A new tag, ConnectIt_Event_TurnEnd, run through the exact same QueueTagSequence
     any other event uses -- so any external system can register a gated response to
     "the turn is ending" (a turn summary, camera reset, whatever) using the identical
     pattern documented in GameEventSubsystem_Workflow.txt, distinct from board-change
     visuals.

Turn-end orchestration is not a board-state concern and doesn't belong on
UConnectIt_BoardSequencerComponent -- it belongs on AConnectIt_BoardManager, which is
already the thing that binds UTurnBasedParticipantManagerComponent for other reasons
(OnActiveControllerChanged).


THE FLOW
--------
  1. A turn ends (NotifyTurnEndSubmitted or HandleTurnTimeout) -> EndTurn() ->
     CurrentPhase = TurnEnd -> OnTurnResolutionStarted.Broadcast().

  2. AConnectIt_BoardManager::HandleTurnResolutionStarted (bound to that broadcast,
     server-only, via BindParticipantManager) fires synchronously during the
     broadcast:
       - Calls ParticipantManagerRef->BeginResolutionHold() immediately -- this is
         what stops EndTurn's own post-broadcast check from advancing the turn.
       - If BoardSequencerComponent->IsIdle() is already true, proceeds straight to
         step 3.
       - Otherwise binds BoardSequencerComponent->OnSequenceIdle and waits.

  3. Once idle (immediately, or once OnSequenceIdle fires), BeginTurnEndSequence()
     resolves UGameEventTaskSubsystem and calls QueueTagSequence with a single step,
     { ConnectIt_Event_TurnEnd }, binding HandleTurnEndSequenceComplete as OnComplete.
     If no subsystem exists, skips straight to step 4.

  4. HandleTurnEndSequenceComplete calls ParticipantManagerRef->EndResolutionHold().
     Since nothing else is holding, the count returns to zero and
     UTurnBasedParticipantManagerComponent::AdvanceToNextParticipant runs immediately.


WHY A COUNTER, NOT A BOOLEAN
-----------------------------
BeginResolutionHold()/EndResolutionHold() are a count, not a flag, so more than one
system can hold resolution back independently without stepping on each other (e.g. if
a second, unrelated system also wants to hold in the future). AConnectIt_BoardManager
only ever places one hold per turn today, but the plugin-side API doesn't assume that.

EndTurn() resets the counter to 0 before broadcasting OnTurnResolutionStarted, so a
bug anywhere that leaves a hold unreleased can never permanently stall every future
turn -- at worst it costs one turn's worth of incorrect early/late advance, not a
stuck game.


WHY THIS LIVES WHERE IT DOES
-----------------------------
UTurnBasedParticipantManagerComponent is generic, project-agnostic plugin
infrastructure -- same isolation principle as UGameEventTaskSubsystem and
UConnectIt_BoardManagerSubsystem (see their own Workflow docs). It must never depend
on UGameEventTaskSubsystem or any ConnectIt gameplay tag, so the hold counter is the
only thing it exposes; it has no opinion on *why* something is holding.

UConnectIt_BoardSequencerComponent stays scoped to board-change visuals only --
turn-end is not a board concern, so it never binds
UTurnBasedParticipantManagerComponent's delegates and knows nothing about resolution
holds. It only answers "am I idle" and fires OnSequenceIdle -- a fact about the board,
usable by anything.

AConnectIt_BoardManager is the natural place for turn-end orchestration: it already
binds ParticipantManager for OnActiveControllerChanged, and it's the actor that owns
BoardSequencerComponent as a sibling, so it's the only thing positioned to combine
"is the board quiet" with "tell the turn system it can advance."
