## Request

"I made some small changes to a few things and now the cursor hover is not working" — asked for help debugging.

## Overview

Traced the full hover pipeline via three parallel investigations: (1) diffed the user's own recent uncommitted changes (retyping `UConnectIt_BoardRegistrySubsystem` to store `UConnectIt_TileRegistry`/`UConnectIt_PieceRegistry` directly, and switching `UConnectIt_BoardRequestMediator`'s board-state resolution to the utility library) — found nothing wrong there; (2) traced `UGridHoverSubsystem` (a pure relay, no tracing of its own — chains a *registered* tile's own `OnGridTileBeginCursorOver` outward) back through `UGridTileRegistryBase::InitialiseRegistry()`'s `DiscoverTiles()`→`RegisterTile()` chain, confirming `AGridCursorManagerBase`/`AGridCursorSimpleBase` aren't used anywhere in this project at all (ConnectIt's hover feedback is pure `Tag_ValidHover`/`Tag_InvalidHover` gameplay tags sent straight to the tile); (3) checked the actual level-config asset content.

**Root cause**: `Content/_ConnectItNetworked/Framework/DeveloperSettings/CI_LevelConfig_Test.uasset`'s `TileRegistry` `Instanced` slot still held a `GridTileRegistryBase`-typed object (the plugin base class) rather than a `UConnectIt_TileRegistry` instance — never re-authored after the `[[2026-09-09-4|2026-09-09-4]]` retype (its `PieceRegistry` slot *had* been correctly migrated to `CI_GridPieceRegistry`, but the tile side was missed). An incompatible `Instanced` property type gets silently nulled on load, so `UConnectIt_BoardRegistrySubsystem::OnWorldBeginPlay` logged `"level config has no TileRegistry template set"` and never created/initialised a `TileRegistry` — so no tile ever registered with `UGridHoverSubsystem`, so hover-changed never broadcast, no matter what the cursor did.

Diagnosis only — the fix (assigning a `UConnectIt_TileRegistry`-class instance to that asset's `TileRegistry` slot, in-editor) was manual, performed by the user. Confirmed fixed.
