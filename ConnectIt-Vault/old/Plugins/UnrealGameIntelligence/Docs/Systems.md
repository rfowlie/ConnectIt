# UnrealGameIntelligence — Systems & Conventions

[README.md](README.md) is the exhaustive per-class reference — every class, its base, its purpose, its key API. This document is the other half: a narrative walkthrough of how the plugin's two loosely-related systems actually work, and the conventions in use across them, for anyone orienting themselves before extending the plugin. Read this first; use README.md to look up a specific class once you know which system it belongs to.

## Systems Overview

### Influence Map Debug Visualization

Lives under `InfluenceMap/`. The problem this solves: an AI system that produces a per-grid-cell scalar (a threat map, a control map, a pathing-cost map) needs some way to be *seen* while it's being tuned, but the plugin has no idea what a "map" is in any given consuming project — it doesn't know the grid coordinate type, the board representation, or how a score is computed. The plugin's answer is to own none of that, and instead define the seams a consuming project's own map and visualiser classes plug into.

Two interfaces do the decoupling, and they're deliberately independent of each other:

- **`IGI_FloatGridDataProviderInterface`** is a "data shape" contract: `float GetData(FIntPoint) const`. A concrete map implements it. Nothing else about the map — how it stores state, how often it updates, what it represents — is the plugin's concern.
- **`IGI_InfluenceMapVisualiser`** is a "rendering lifecycle" contract: `GetTag`/`GetDisplayName` for identity, `Activate`/`Deactivate`/`IsActive` for showing and hiding a debug representation in the world. A concrete visualiser implements it, and separately exposes its *own*, project-specific typed setter (e.g. `SetFloatGridDataProvider`) that accepts a `TScriptInterface<IGI_FloatGridDataProviderInterface>` — the visualiser is what wires a map to a rendering, not the plugin.

**`UGI_InfluenceMapSubsystem`** is the registry/orchestrator sitting on top of both, and it only ever touches the visualiser side: it holds an ordered `TArray<TScriptInterface<IGI_InfluenceMapVisualiser>>`, deactivates whatever's currently selected before activating the next one (`SelectVisualiser`/`SelectVisualiserByIndex`), and owns the create/show/hide/destroy lifecycle of a `UGI_InfluenceMapWidget` debug widget. The subsystem is intentionally unaware that data providers exist at all — that pairing happens entirely at the consuming project's construction site, before a visualiser is ever registered.

**`UGI_InfluenceMapWidget`** is the abstract UMG base for the debug UI: the subsystem calls its `SetupButtons(Tags)` (a `BlueprintImplementableEvent`, so button layout is a Blueprint concern) whenever the registry changes, and listens for the widget's `OnSelectionChanged` delegate to drive selection back through `SelectVisualiser`. Communication is one-way-out from the widget — it never holds a reference back to the subsystem.

This data-provider / visualiser split means one visualiser type (say, a generic float-overlay renderer) can work with *any* map that produces a float-per-cell score, and one map can in principle be paired with more than one visualiser. It's the same shape as the plugin's other "define the seam, not the implementation" instinct, and it's worth following for any future debug-visualization work added here.

*(A supplementary, non-Docs design guide — `Source/UnrealGameIntelligence/README/InfluenceMap_README.md` — extends this pattern with guidance on building **composite** maps, i.e. maps that internally combine other maps. Its patterns are sound, but its code samples are written against an interface name, `IGI_InfluenceMap`, that doesn't actually exist in the plugin; see Known Rough Edges.)*

### MinMax Solver Toolkit

Lives under `MinMax/`. The problem this solves: a classic game-tree search (minimax, optionally with alpha-beta pruning and move ordering) is a well-understood algorithm family that shouldn't need to be rewritten per project — but it does need to stay generic over whatever node/board representation a project actually uses. The plugin's answer is header-only function templates constrained by C++20 `requires`-concepts, rather than a class hierarchy: a node type opts in simply by having the right member functions, with no interface to implement or base class to derive from.

Three solvers exist side by side in `MinMax/`, and reading them together tells a clear progressive story:

1. **`MinMaxAlgorithm::Solve`** — the baseline. No pruning at all: recurse to every leaf, take the max at maximiser levels and the min at minimiser levels. Constrained by the simplest concept, `c_min_max_node<TNode>` (just `GetChildren()`).
2. **`MinMaxABPruningAlgorithm::Solve`** — the same recursion, now carrying `Alpha`/`Beta` bounds through the call stack and breaking out of a children loop early once `Beta <= Alpha` — a branch can never affect the final result once the opponent already has a better alternative elsewhere in the tree. Same `c_min_max_node<TNode>` constraint as the baseline; alpha-beta pruning doesn't need anything extra from the node type.
3. **`MinMaxABMoveOrderAlgorithm`** — the same alpha-beta recursion again, but children are sorted by a per-node `GetOrderingScore()` (via `GetOrderedChildren`) before being visited, so the most promising branches are searched first and cutoffs happen sooner. This needs more from the node type, hence a stricter concept, `c_min_max_move_order<TNode>`, which additionally requires `GetOrderingScore()`.

Each step adds exactly one idea on top of the last — pruning, then ordering — while leaving the previous step's solver in place rather than replacing it, so a consumer can pick whichever tier of sophistication (and node-type requirements) fits. Read them in that order (`MinMaxAlgorithm.h` → `MinMaxABPruning.h` → `MinMaxABMoveOrder.h`) to see the technique build up.

Sitting alongside these three is **`MinMaxUtility.h`**, which is a different kind of thing entirely — not a solver, but a grab-bag of node concepts (`c_min_max_node`, `c_min_max_move_order`, `c_min_max_tree_builder`, and a second, incompatible generation `c_min_max_node_2`/`c_child_builder`/`c_game_over_predicate`/`c_move_orderer`/`c_evaluator`) plus free-function tree-building helpers (`BuildNodeRecursive`, and a threaded variant, `BuildNodeRecursiveWithThreadDepth`, that fans work out across `UE::Tasks` up to a configurable depth before falling back to serial recursion). The file also defines **`MinMax::TMinMaxManager<TNode>`**, an abstract template class wrapping tree queries (`CountNodes`, `GetDeepestDepth`) around three pure-virtual async entry points (`BuildTreeAsync`, `EvaluateTreeAsync`, `BuildAndEvaluateTreeAsync`) that a concrete subclass would need to implement. No such subclass exists anywhere in this plugin — it reads as scaffolding for a higher-level, UObject-friendly wrapper around the three solvers above that was started and never finished. See Known Rough Edges for where the trail of this abandoned direction picks up again outside the plugin.

### Utility Score Debug Interface

Lives under `Utility/Interface/`. The smallest piece: `IUtilityScoreHandler` is a four-method `BlueprintNativeEvent` contract (`GetUtilityScore`/`SetUtilityScore`/`ShowUtilityScore`/`HideUtilityScore`) for exposing a single float "how good is this option" score to an on-screen debug overlay. It doesn't participate in either system above — no dependency on the influence-map registry or the MinMax templates — it's a standalone, minimal seam for a different flavour of AI debugging (scoring a candidate action or option, rather than visualising a whole grid).

## Conventions

- **Type prefixes are folder-scoped, not plugin-wide**: everything under `InfluenceMap/` carries a `GI_` infix on top of the standard `U`/`I`/`F` prefix (`UGI_InfluenceMapSubsystem`, `IGI_InfluenceMapVisualiser`, `FGI_OnInfluenceMapVisualiserSelected`) — readable at a glance as belonging to this plugin's Influence Map system specifically. `MinMax/` and `Utility/` don't follow this — `MinMaxAlgorithm`, `IUtilityScoreHandler`, etc. carry no plugin-specific infix at all. There's a further small inconsistency inside `InfluenceMap/` itself: interface *files* always end in `...Interface.h` (`GI_FloatGridDataProviderInterface.h`, `GI_InfluenceMapVisualiserInterface.h`), but only one of the two interface *class names* actually keeps the `Interface` suffix (`IGI_FloatGridDataProviderInterface` does; `IGI_InfluenceMapVisualiser` doesn't).
- **Delegates are dynamic, `FGI_On<Event>`-named, and two-param tag+index**: both delegates in the plugin (`FGI_OnInfluenceMapVisualiserSelected`, `FGI_OnInfluenceMapWidgetSelectionChanged`) are `DECLARE_DYNAMIC_MULTICAST_DELEGATE_TwoParams`, carry `(FGameplayTag Tag, int32 Index)`, and follow the same `FGI_On<Event>` naming shape. A small, consistent pattern — but it's only ever been exercised twice, so treat it as an observed default rather than a documented rule.
- **`Category` strings differ by folder, not randomly**: `InfluenceMap/` classes consistently use an abbreviated, no-space, pipe-delimited style — `"GI|InfluenceMaps"`, `"GI|InfluenceMaps|UI"`. `Utility/Interface/UtilityScoreHandler.h` instead spells the plugin name out with spaces around the pipe — `"GameIntelligence | Utility"`. Two internally-consistent styles, not reconciled with each other; match whichever folder you're adding to.
- **The MinMax folder's C++20 `requires`-concept style is unique to this plugin**: nowhere else in the codebase constrains templates this way. The pattern is: define a `concept c_<name><TNode>` naming exactly the member functions a node type must expose (e.g. `c_min_max_node` requires only `GetChildren()`; `c_min_max_move_order` additionally requires `GetOrderingScore()`), then gate each template function with `template<typename TNode> requires c_<name><TNode>`. No inheritance, no interface — a node type satisfies a solver purely structurally. When extending this family, prefer adding a new, narrowly-scoped concept over widening an existing one, so an older, simpler node type doesn't have to grow methods it doesn't need just to keep compiling.
- **Comment density is high in `InfluenceMap/` and uneven in `MinMax/`**: the Influence Map headers are heavily documented — full doc-comments explaining lifecycle, usage patterns, and even a worked example (`GI_FloatGridDataProviderInterface.h`) — though that same worked example is where the stale `IGI_InfluenceMap` reference lives (see Known Rough Edges), so thorough commenting hasn't guaranteed the comments stayed accurate. `MinMax/` swings between terse (`MinMaxAlgorithm.h`, `MinMaxABPruning.h` — a line or two per branch explaining the cutoff logic) and essentially bare (`MinMaxABMoveOrder.h`'s `GetOrderedChildren`, `MinMaxUtility.h`'s concept definitions), plus two blocks of dead, commented-out code kept as historical reference rather than removed.
- **Folder/file organization**: one subfolder per system under both `Public/` and `Private/` (`InfluenceMap/`, `MinMax/`, `Utility/Interface/`), one class per header/cpp pair, `#include`s relative to `Public/` (e.g. `#include "InfluenceMap/GI_InfluenceMapVisualiserInterface.h"`). The MinMax templates are the one exception to "one class per pair" in spirit — they're free functions and concepts grouped by algorithm, not classes, but still one file per algorithm.

## Known Rough Edges

This plugin doesn't have its own cross-cutting duplication/issues file the way the consuming project does — these are noted here rather than starting a second file for one plugin's internal findings. Each also has a pointer from the relevant row in [README.md](README.md)'s class tables.

- **A phantom `IGI_InfluenceMap` / `UGI_InfluenceMap` interface is referenced twice, but implemented nowhere.** `GI_FloatGridDataProviderInterface.h`'s own in-header usage example shows a concrete map implementing `IGI_InfluenceMap` "(plugin contract)" alongside a shortened `IGI_FloatGridDataProvider` (dropping the real class's `Interface` suffix), and the standalone `Source/UnrealGameIntelligence/README/InfluenceMap_README.md` design guide builds its entire composite-map pattern around the same `IGI_InfluenceMap`/`UGI_InfluenceMap` name, complete with a `SetUpdateDelegate` method that has no counterpart anywhere in the shipped interfaces. The actual, compiling contract is the two-interface split documented above (`IGI_FloatGridDataProviderInterface` + `IGI_InfluenceMapVisualiser`) — neither has a `SetUpdateDelegate` concept. Best guess: an earlier design pass unified identity + data-shape + update-timing into one interface, the implementation was later split in two during a refactor, and the doc comment plus the separate design guide were never updated to match. See [README.md](README.md#influencemap) for the class table entries this affects.
- **`MinMaxABMoveOrderAlgorithm` has no public entry point.** Both `MinMaxAlgorithm` and `MinMaxABPruningAlgorithm` expose a callable `Solve(...)`; the move-ordering variant's equivalent function is named `SolveInternal` and nothing in the file wraps it in a public-facing `Solve`. A consumer can still call `SolveInternal` directly since it's not actually private (there's no class, just a namespace), but the naming signals it was meant to be an implementation detail behind a wrapper that was never written. Its sibling helper, `GetOrderedChildren`, also contains a stray `Ordered.Reserve()` call with no argument, gated behind `if (bIsMaximisingPlayer)` — this compiles (only because the function template isn't instantiated by anything in-plugin) but does nothing at runtime beyond the gate check itself. See [README.md](README.md#minmax).
- **`MinMaxAlgorithm.h`** contains ~50 lines of a commented-out `TMinMaxAlgorithm` struct — an earlier, differently-shaped version of the same baseline solver, kept as historical reference per its own inline comments (which even annotate specific "bug fix" deltas from the live version). See [README.md](README.md#minmax).
- **`TMinMaxManager<TNode>` (`MinMaxUtility.h`) is orphaned scaffolding.** It's a live, compiling abstract template class — not commented out — but has no concrete subclass anywhere in this plugin, so its three pure-virtual async entry points (`BuildTreeAsync`/`EvaluateTreeAsync`/`BuildAndEvaluateTreeAsync`) have never actually been exercised. The same file also carries ~135 lines of a commented-out `TMinMaxManagerBase` class that looks like a more complete draft of the same idea (delegate-injected build/evaluate steps, async dispatch via `UE::Tasks`, GC-safe callback via `TWeakObjectPtr`). The trail continues outside this plugin: the consuming project has its own `ConcreteMinMaxExample.h`, entirely commented out, that goes a step further and sketches a three-level hierarchy (a `TMinMaxManagerBase` pure-C++ template → an abstract UObject base → a concrete subclass) built on top of this plugin's own solver templates — evidence that someone did once attempt to route the consuming project's AI through this scaffolding before abandoning the attempt in favor of the project-specific implementations described in the next point. See [README.md](README.md#minmax).
- **The consuming project's own MinMax implementations don't use this toolkit at all.** Its two *live* (not commented-out) tree-search classes are unrelated to both this plugin's solver templates and to the abandoned `TMinMaxManager`-based attempt above — see the project-level [duplication notes](../../../Source/ConnectIt/Docs/Duplication.md) for the full account of that split. Anyone picking this toolkit back up should treat it as a genuinely clean slate rather than assuming it already has a consumer to learn conventions from.
