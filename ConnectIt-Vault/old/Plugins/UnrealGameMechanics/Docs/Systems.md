# UnrealGameMechanics — Systems & Conventions

[README.md](README.md) is the exhaustive per-class reference — every class, its base, its purpose, its key API. This document is the other half: a narrative walkthrough of how the plugin's systems fit together, and the conventions actually in use across them, for anyone orienting themselves before extending the plugin. Read this first; use README.md to look up a specific class once you know which system it belongs to.

## Systems Overview

### Tag Broadcasting (`Broadcasters/`)
The simplest system in the plugin: `IGameplayTagBroadcaster` is a register/unregister contract for a one-tag-param callback, and `UGameplayTagBroadcasterComponent` is a concrete, drop-in `UActorComponent` realization of the same idea (a `BlueprintAssignable` multicast delegate plus a protected `Broadcast(Tag)`). The two aren't actually linked — the component doesn't implement the interface — so treat them as two independent, small building blocks for "something needs to announce a tag happened" rather than one cohesive abstraction.

### Gated Event Sequencing (`GameEvent/`)
The plugin's most developed system, and the one most other systems (and the consuming project's own visual-sequencing workflow) are built on. Two layers:

- **`UGameEventTaskManager`** is the phase-barrier primitive: register a set of objects/async tasks against it (optionally phased via an integer), call `InitiateAllTasks()`, and it only fires `OnManagerComplete` once every task in every phase has genuinely finished — not just started.
- **`UGameEventTaskSubsystem`** is a per-world registry of these managers, keyed by gameplay tag, created lazily on first use. Its single public firing mechanism is `QueueTagContainer(Tags)`: every call enqueues a `FGameplayTagContainer` into a serialized FIFO queue (`ContainerQueue`). Every tag inside one queued container fires **in parallel**; the queue only advances to the **next** container once every tag in the current one has fully completed. The underlying single-tag `TriggerTag` is private — there is deliberately no way to fire a tag from outside the queue.

This gives two independent binding styles depending on what a listener needs: `BindOnTagBegin`/`BindOnTagComplete` for "just tell me when this tag starts/finishes, no gating," or registering a `UGameEventTask_Async` (with its `OnExecuteDelegate`/`OnComplete` pair, optionally `bIsPersistentTask` to auto-re-register on every future trigger) for "run my work and make the rest of this container's completion wait on me."

*(An older multi-step chaining primitive, `QueueTagSequence`, has been fully removed from `UGameEventTaskSubsystem` — `QueueTagContainer` is its complete replacement. A few stale header comments still name the old primitive; see Known Rough Edges.)*

### Turn Bookkeeping (`GameTurn/`)
Smaller, more mechanical: `UGameTurnHandler` wires two `UGameEventTaskManager`s (one for turn-start, one for turn-end) to four public pre/post-async delegates, so a turn boundary can itself be a gated event. `UGameTurnTracker` is a trivial counter. `UGameTurnParticipant`/`UGameTurnParticipantComponent` are a near-duplicate pair (same four Begin/End/Pause/Resume delegates, one as a plain `UObject`, one as a component, no shared interface) — see README's Known Discrepancies.

### Input Binding with an Explicit Lifetime (`Input/`)
`UInputTagBinder` builds one `UInputMappingContext` from a designer-authored `TArray<FInputTagBinding>` and scopes it to an explicit `Initialise` → `BindAll`/`UnbindAll` lifecycle, rather than EnhancedInput's usual "add the mapping context once at `BeginPlay` and leave it running" assumption. This matters for any consumer whose own lifetime is itself dynamic — an entry that gets pushed and popped on an action stack, for instance, shouldn't have a permanently-active input mapping. Every bound `InputAction` funnels through one shared `OnInputTagTriggered` delegate carrying the matching entry's `BindingTag`, so a consumer switches on the tag in one place instead of binding a separate function per input — adding a new bound input is purely a data change (one more `FInputTagBinding` entry), no new C++.

### Actor Pooling (`Pooling/`)
Standard object-pool shape: `UActorPool` holds per-class active/inactive sets and grows on demand; `UActorPoolSubsystem` is the per-world registry keyed by actor class, with a reverse actor→pool lookup so a caller releasing an actor doesn't need to remember which pool it came from. `IActorPoolInterface` lets a pooled actor hook its own show/hide logic into activation/deactivation instead of the pool forcing a default hidden/no-collision/no-tick state on it.

### Scoring & Selection (`Scoring/`)
A small, self-contained toolkit for "I have several candidates with scores, now what": `GetSortedKeysByValue<K,V>` (a generic sort-a-map-by-value template), `FObjectScore`, and a `UBlueprintFunctionLibrary` exposing `ScoreSelect_TopN` (weighted random pick among the top N) and `ScoreModify_RandomNoise` (per-key uniform noise, e.g. to break ties or add unpredictability before a selection).

### State Management
Two structurally distinct patterns coexist here, and it's worth being deliberate about which one a new use case actually needs:

**Single-state** (`UGameMechanicsStateBase` / `UGameMechanicsStateSimple`) — one object *is* the current state, entered and exited in place. `GameMechanicsStateBase` wraps `Enter()`/`Exit()` around a protected `_Internal` `BlueprintNativeEvent` and fires enter/exit delegates; `GameMechanicsStateSimple` skips the wrapper and exposes `Enter()`/`Exit()` as direct native events with a single completion delegate. Good fit for a flow that's genuinely one state at a time with no need to remember or return to a previous one.

**Stacked state machine** (`UStackedState` / `UStackedStateMachine`) — an actual stack. `UStackedStateMachine` owns a `TArray` of `UStackedState` entries: `SetBaseState` replaces the whole stack with one entry; `PushState` layers a new entry on top, either fully tearing down what's beneath (`bDeinitialize=true`) or leaving it running underneath, effectively paused; `PopState` returns to whatever's below the current top (and refuses to pop the last remaining entry, so the stack can never go empty). A state never mutates the stack itself — it broadcasts one of three transition-request delegates (`OnSetBaseState`/`OnPushState`/`OnPopState`), and the machine is what's actually bound to them, added on push and (mostly) removed on pop. This is the right fit when a flow has **nested or resumable sub-phases** — e.g. a multi-step action that walks a player through several distinct selection phases, where "go back a step" is a real, meaningful operation, not just "start over."

This system was ported from an external, unrelated project's existing stack-based state pattern — kept functionally as-is (see Known Rough Edges for the handful of carried-over quirks) and renamed to be project-agnostic, since nothing about a stack-based state machine is specific to any one game. It does not replace the single-state pair; **there is no in-repo policy yet on which to reach for**. As a rule of thumb (a suggestion, not documented policy): reach for the single-state pair for a simple one-shot flow, and the stacked machine when a flow has real nested/resumable sub-phases a simple state can't express.

### Debug Widgets (`Debug/`, `Widget/`)
`UDWidgetBase` is the shared contract for a **one-debug-widget-per-tracked-class** family: `NativeConstruct` binds delegates once and does an initial refresh; `NativeDestruct` unbinds once. A concrete subclass overrides three protected virtuals — `BindDelegates()` (resolve the tracked source, bind to it), `UnbindDelegates()` (mirror), `RefreshFields()` (re-read every cached field; must tolerate the source not existing yet, since it runs both before and after the source may resolve). `RefreshAll()` re-runs `RefreshFields()` then fires one coarse `OnDebugStateUpdated()` `BlueprintImplementableEvent` — one event per widget, not split per field, since each widget's field set is small. `UDWidgetBase` has no show/hide API of its own; visibility is left to ordinary `UUserWidget`/UMG mechanisms. `UDWidget_GameEventTaskSubsystem` is the one concrete tracker currently in this plugin, watching `UGameEventTaskSubsystem`'s `OnActiveManagerTagsChanged` and caching the in-flight tags from `GetTagsInQueue()`.

## Conventions

- **Type prefixes**: standard `U`/`I`/`F`/`E` throughout (no `A`-prefixed actors exist in this plugin). Debug widgets layer a sub-convention on top: `UDWidget_<TrackedClassName>` — the class being tracked is directly readable from the widget's own name (`UDWidget_GameEventTaskSubsystem` tracks `UGameEventTaskSubsystem`).
- **Delegates are exclusively dynamic** — every delegate in this plugin is `DECLARE_DYNAMIC_DELEGATE*`/`DECLARE_DYNAMIC_MULTICAST_DELEGATE*`; there are no native (`DECLARE_DELEGATE`/`DECLARE_MULTICAST_DELEGATE`) declarations anywhere, and no dual-declared dynamic+native pairs for the same event (contrast this with `UnrealTurnBasedMechanics`, which pairs every dynamic delegate with a native sibling — that convention hasn't propagated here). Naming itself is inconsistent between two coexisting styles: `F<Context>Delegate` (`FGameStateDelegate`, `FGameTurnHandlerDelegate`) and `FOn<Event>` (`FOnActiveManagerTagsChanged`, `FOnInputTagTriggered`) — pick either when adding a new one, but expect to see both.
- **The `_Internal`-wrapper vs. direct-`BlueprintNativeEvent` split is real and unresolved**: `UGameMechanicsStateBase` wraps a public non-event method around a protected `_Internal`-suffixed native event (bookkeeping/delegate-firing happens in the wrapper, the override point is the `_Internal` hook). Nearly everything else in the plugin — `UGameMechanicsStateSimple`, `UStackedState`'s `Initialize`/`Deinitialize`, every interface (`IGameplayTagBroadcaster`, `IGameEventTaskHandler`, `IGameStateHandlerInterface`) — exposes `BlueprintNativeEvent`s directly with no wrapper. The newer Stacked State code follows the majority (direct-event) style; it didn't introduce this split, it just didn't resolve it either.
- **`Category` strings are genuinely inconsistent** — verbatim examples actually in the source: `"Game Mechanics | Turn"` (pipe with spaces), `"GameMechanics|Framework"` (pipe, no spaces, no space in the plugin name either), `"Actor Pool"` / `"Turn Completion"` / `"State Machine"` / `"Debug"` / `"Input"` (single/double plain words, no delimiter), `"Scoring | Selectors"` vs `"Scoring | Modifiers"` (consistent with each other, inconsistent with the rest). No canonical style has won out; pick whichever feels closest to a neighboring class in the same subfolder rather than inventing a fourth style.
- **Folder/file organization**: one subfolder per system, mirrored under both `Public/` and `Private/` with matching names; one class per header/cpp pair; an interface always gets its own file, never bundled with a concrete implementer; shared top-level enums/structs live in `UnrealGameMechanicsEnums.h`/`UnrealGameMechanicsStructs.h` rather than inside a system's own folder. Cross-references `#include` relative to `Public/` (e.g. `#include "GameEvent/GameEventTaskManager.h"`).
- **Static `Create()` factories exist but aren't the only construction path, and aren't always the right one** — `UGameEventTaskManager::Create()`, `UGameTurnHandler::Create()`, and `UActorPool::Create(...)` all offer one, but `UGameEventTaskSubsystem::GetOrCreateManager` deliberately uses `NewObject<UGameEventTaskManager>(this)` instead of the class's own `Create()`, specifically because `Create()` defaults to the transient package with no owner — outering to the subsystem instead gives a correct GC ownership chain (the subsystem's `ManagersByTag` map, itself a `UPROPERTY`, keeps every manager reachable for the world's lifetime). Worth remembering when adding a new class with a `Create()` helper: it's a convenience for simple/unowned cases, not a substitute for thinking about ownership when the object needs to survive garbage collection tied to something specific.
- **Comment density is bimodal**, and it roughly tracks how recently a system was touched. Older code (`Broadcasters/`, `GameTurn/`, most of `Pooling/`/`Scoring/`, the original `State/` pair) has essentially no rationale comments beyond the generated `/** * */` stub. Newer or more recently revisited code (`GameEventTaskSubsystem`, `InputTagBinder`, both Stacked State files, both Debug widget files) carries dense prose explaining *why* — including specific historical bug-fix notes (e.g. `GameEventTaskSubsystem`'s comments on exactly what ordering bug the "populate `ActiveManagerTags` before triggering anything" guard prevents). When touching an older, sparsely-commented class, matching the newer style's rationale-first approach is a reasonable default rather than matching the sparser original.

## Known Rough Edges

This plugin doesn't have its own cross-cutting duplication/issues file the way the consuming project does — these are noted here rather than starting a second file for one plugin's internal findings. Each also has a pointer from the relevant row in [README.md](README.md)'s class tables.

- **`IGameEventTaskHandler`** — orphaned. `UGameEventTaskSubsystem` no longer implements it (it once did, per its own stale header comments — see below), and nothing else in the plugin does either.
- **Stale comments in `GameEventTaskSubsystem.h`** reference a `QueueTagSequence` function and its `HandleSequenceStepTagComplete` handler by name in three places — that primitive has been fully removed from the class; only the comments remain. Worth a cleanup pass independent of any doc change.
- **`UStackedStateMachine::PopState()`** calls `Deinitialize()` directly on the popped state rather than `DeinitializeState()` — unlike `SetBaseState`/`PushState`-with-`bDeinitialize`, this means a popped state's `OnSetBaseState`/`OnPushState`/`OnPopState` bindings to the machine are **not** unbound on pop. Self-flagged in a `.cpp` comment as a deliberate "keep it as-is for now" carried over from the ported source, explicitly worth revisiting rather than a hidden landmine.
- **`UStackedStateMachine::SwapState()`** is public and `BlueprintCallable`, but its body is just comments — calling it currently does nothing, silently.
- **`PeakState()`** is a verbatim misspelling of "Peek," carried over unchanged from the ported source.
- **`FGameplayTagValueProbability::operator==`** takes an `FGameplayTagValuePair` as its parameter rather than its own type — almost certainly a copy-paste artifact; harmless today since nothing invokes equality between the two types.
- **`FInputTagBinding.h`** carries a live, open TODO questioning whether `BindingTag` needs to be passed alongside `FInputActionInstance` at all, or whether the instance alone could be used to branch on.
- Small dead-code scraps, no functional impact: a commented-out `UGameEventTask_Async::Create()` factory stub in `GameEventTask_Async.cpp`, and a commented-out `IActorPoolInterface::IsPoolObjectActive()` declaration.
