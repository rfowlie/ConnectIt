## Request

"In BP widgets what would be an ideal setup for creating a scoreboard UI" — the user's
own plan was a `CIW_ScoreBoard` frame widget containing N `CIW_ScoreBoard_Element` row
widgets (one per player) stacked in a `VerticalBox`; asked whether that shape was right
and, for each recommendation, how each widget should actually get its data.

## Overview

Guidance-only session — no code changed, and nothing here could be built by Claude Code
directly (Blueprint graphs are binary `.uasset` data). Both `CIW_ScoreBoard` and
`CIW_ScoreBoard_Element` already existed as content assets at the time, confirming the
user's plan.

Confirmed the two-widget split is correct (idiomatic UMG "frame + list of rows" shape)
and refined the responsibility split, all against the accessors added earlier the same
day ([[ConnectIt/logs/2026-09-04|2026-09-04]]):

- **`CIW_ScoreBoard` (frame)** — structural only: build rows once (participants are fixed
  once the match starts), not a reactive display. Resolve
  `UConnectIt_GameUtilityLibrary::GetConnectItGameState`; build immediately if
  `GetParticipants()` is already populated at `Construct`, otherwise bind
  `ATurnBasedGameState::OnMatchPhaseChanged` and build the first time `MatchPhase` leaves
  `WaitingForParticipants`. One `Initialize(int32 FactionSlot)` call per row at creation;
  no `Slot → Widget` map needed since rows are self-sufficient (below). Frame-level-only
  values: `GetTargetScore()`, `GetMatchPhase()`/`OnMatchPhaseChanged`.
- **`CIW_ScoreBoard_Element` (row)** — stores exactly one variable (`FactionSlot`),
  resolves and binds everything else itself at `Initialize`, seed-then-push (same shape
  as the `DWidget_*` family, re-scoped to one row instead of one class):
  - Identity: `GameState->GetParticipantBySlot(FactionSlot, bOutValid)` →
    `UTurnBasedMechanicsLibrary::GetParticipantDisplayName`; cache the cast
    `ATurnBasedPlayerState` for `OnReadyChanged`/`OnForfeited`/`OnTurnsMissedChanged`.
  - Score/progress: seed via `GetFactionScore`/`GetFactionScoreProgress`, then bind
    `UBoardStateComponentBase::OnBoardStateChanged` (zero-param — re-pull both numbers on
    every fire, don't try to diff the event) via
    `UConnectIt_GameUtilityLibrary::GetBoardStateComponent`, or the
    `UConnectIt_BoardManagerSubsystem`/`OnBoardManagerReady` late-binding route if the
    board might not exist yet when the row constructs.
  - Turn highlighting: **do not** compare `FactionSlot` to the raw
    `ActiveParticipantIndex` (that's an array index, not a slot index — they only
    coincide by registration-order convention). Bind `OnParticipantIndexChanged` and
    compare `GameState->GetActiveParticipant(bOutValid).SlotIndex` instead; seed the same
    check once at `Initialize` too.
  - Faction colour/icon: **not available** — flagged as the deferred Gap 1 from the same
    day's session (see [[ConnectIt/decisions/2026-09-09-faction-visuals-subsystem-built-then-removed|faction-visuals decision]]). Recommended a hardcoded per-slot colour array in
    the row's own Blueprint as a stand-in until/if that subsystem comes back.
  - Recommended rows self-bind rather than the frame routing updates to children by
    index — no routing plumbing to maintain, and the cost (redundant per-row re-queries
    on a shared zero-param signal) is a non-issue at this game's scale (2-4 factions).

Wrote the recommendation to the session's plan file and called `ExitPlanMode` to present
it; **the user rejected/interrupted that call** before it completed — the guidance above
was delivered in chat regardless, but was never formally "approved" as a plan. No
in-editor changes are known to have followed directly from this exchange within the
conversation itself.
