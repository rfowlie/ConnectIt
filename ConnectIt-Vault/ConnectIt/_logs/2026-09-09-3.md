## Request

Explain the reasoning behind resolving `UConnectIt_LevelConfigDataAsset` through `UConnectIt_LevelConfigSettings` (a `UDeveloperSettings`) rather than through a `GameInstance`/`GameInstanceSubsystem` — asked whether it's mainly about designer ease-of-configuration.

## Overview

Pure explanation, no code touched. Covered: `UDeveloperSettings` resolves via `GetDefault<T>()` with zero live-object dependency (works outside any session, e.g. editor/cook-time validation — a `GameInstance` structurally can't); it matches the project's existing "every machine resolves the same static data independently" philosophy for free, since `Config=Game, DefaultConfig` bakes the map into each machine's own `.ini`; `DefaultConfig` gives a Project Settings UI *and* auto-persistence to a diff-friendly text file, versus a GameInstance Blueprint's binary-asset-backed Details panel; and it keeps responsibility boundaries clean — a level→asset map is static authored config, not live session state, so routing it through GameInstance would borrow the wrong lifecycle tool. Also noted the heavier `UAssetManager`/`PrimaryAssetType` alternative was already explicitly considered and rejected (per the class's own header comment) as over-engineering for one flat mapping.
