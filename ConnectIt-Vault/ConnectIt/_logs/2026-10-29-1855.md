## Decision (owner)

**Tag ↔ class: option 1.** Save stability comes first: actions stay keyed by tag in the save and rewards (a tag
survives renames and moves; a class path wouldn't).
- Each action shard table entry names its action class.
- An item action's class comes from the item inventory asset.
- Considered and rejected:
  - a separate tag → class asset (another list to keep in sync);
  - keying the save by class (saves would break on Blueprint renames, and Stage 1 would need reworking).

## Overview

- **Shard table:** `FConnectItActionShardCosts::ActionClass`. Validation errors on a missing class or a class whose
  tag isn't the key.
- **Rules on `FConnectItAdventureProgress`:**
  - `GetNodeState` (`EConnectItNodeState`: Hidden / Available / Gated / Completed; "revealed" comes from the hub);
  - `CanBreakSeal` (with a reason) and `BreakSeal` (spends the gate's seals; the seal stays broken);
  - `RecordResult`: win or lose, the match's inventory is written back and the node becomes the last played. On a
    first win the node is completed and its rewards granted; items are capped by the item inventory asset, and ones
    it doesn't list are skipped with a warning;
  - `FindActionClass` (tag → class) and `GetItemCount`.
- **`UConnectIt_AdventureSaveGame`** holds the progress and a `SaveVersion`.
- **`UConnectIt_AdventureSubsystem`** (game instance) loads the "Adventure" slot on start, saves after each change,
  and exposes the queries and changes to Blueprint.
- Tests: new `ConnectIt.Adventure.NodeState` and `.Results`. `.ShardTable`'s falling-costs case now uses a real
  action, because entries need a class. Editor build clean, **75/75**; Game target clean.
