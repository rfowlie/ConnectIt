## Request

Discussed the open question `action-gameplay-tags` (why action identity is set in 4-5
disconnected places) — owner had traced part of it to `ActionTag` being an Instanced
sub-object property that silently diverges between a placed action's own copy and the
class defaults. Asked to update the question note with findings but explicitly hold off on
applying any fix while they think it over further.

## Overview

Root-caused one of the note's four places: `Loadout.Actions[]` is `Instanced`
(intentionally, for the per-controller runtime-clone pattern), but `ActionTag` on
`UTurnBasedActionBase` is plain `EditAnywhere`, so it rides along as a per-placement
editable field that diverges from the class defaults the moment an instance is placed and
the class defaults are later changed — not caused by `DefaultToInstanced` on the action
classes (that's a different, correctly-relied-upon mechanism elsewhere). Confirmed the
fix isn't a C++ access-level change (`protected`/`private` don't control editor exposure)
but a UPROPERTY specifier change (`EditDefaultsOnly`), with a stronger code-derived
alternative also on the table. Also distinguished this from the separate
`RequiredActionTagA`/`RequiredActionTagB` duplication (a different object, no Instanced
mechanics involved) and floated a candidate direction for that one. No code changed — per
the owner's request, this stays a discussion captured in the question note, not yet acted
on.
