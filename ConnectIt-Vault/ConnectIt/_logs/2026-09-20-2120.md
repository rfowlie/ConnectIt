## Request

Owner asked how the Actions UI's "push this action class" reaches the actions component, and whether
the action should get its runtime state from the PlayerState.

## Overview

- Answered: no instance is created at push time. `TryPushActionByClass` finds the one instance built
  from that class at `InitialiseFromLoadout` (one per config entry, reused every turn) and calls
  `TryPushActionByRef`. Runtime state is not applied to instances; the PlayerState is consulted
  (client `CanActivate`, server Mediator gate).
- **Fixed a bug:** `TryPushActionByClass` discarded `TryPushActionByRef`'s result and returned true
  whenever the instance existed, so a refused push (limbo, awaiting confirmation, `CanActivate` false)
  looked like success to the UI. It now returns the real result; header comment corrected.
- **Owner chose pull accessors** over a push/snapshot hook: `UTurnBasedAction` gained read-only
  BlueprintPure getters that read the owner's PlayerState on every call, storing nothing on the
  instance (no second copy that could go stale): `GetPermanentRuntimeState`, `GetNumberedRuntimeState`,
  `GetUsesThisTurn`, `GetMaxUsesPerTurn`, `GetUsesRemaining`. `ATurnBasedPlayerState` gained
  `GetPermanentRuntimeState` / `GetNumberedRuntimeState` (copy one entry's state, bool + out).
- Builds clean; not PIE-tested.
