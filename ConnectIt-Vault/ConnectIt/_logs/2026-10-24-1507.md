## Request

The owner's review of player actions Stage 3:

- grants must be able to add item actions the player doesn't hold yet;
- caps are the game's static tuning, in a data asset, not a parameter or a per-entry field;
- an item action the asset doesn't list can't be held (every item action has a cap);
- no zero-count inventory entries;
- design note: the core actions will very likely not be item actions.

## Overview

- **New plugin data asset** `UItemActionInventoryDataAsset`:
  - `MaxHeld`: item action → cap, at least 1; `GetMaxHeld` returns 0 for an unlisted action;
  - validation;
  - `Get()` from new plugin project settings, `UTurnBasedMechanicsSettings` (Project Settings > Plugins > Turn Based
    Mechanics > Item Inventory).
  - The plugin gains a `DeveloperSettings` dependency.
- **`FItemActionEntry`** is now action + count (at least 1).
- **PlayerState:**
  - seeding drops entries holding none and unlisted actions (with a warning), clamping counts to the cap;
  - `GrantItems` adds an action not yet held, clamped to its cap (0 and a warning for an unlisted action);
  - spending the last item removes its entry.
- **Build and tests:** built; 69/69 tests pass.
  - The item test now installs a test caps asset in the settings for its duration.
  - It covers: an action granted that wasn't held, unlisted actions dropped and refused, and the last item leaving
    the inventory.
- **Vault:**
  - **The plan:** the design lean in its Context, Stage 3's as-built revised, Stage 5 trimmed (the action shard
    table holds shard costs only), "Settled after Stage 3".
  - **The decision note:** caps in a game-static asset.
  - **`design/adventure-hub.md`:** the design lean.
