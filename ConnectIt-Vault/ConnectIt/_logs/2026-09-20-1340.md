## Request

Owner is rebinding the Actions UI to PlayerState entries and needs an action's max uses per turn
at runtime; also wants temporary changes to it (e.g. 2 -> 1 for a few turns) to be possible.

## Overview

- `MaxUsesThisTurn` (already added by the owner to `FPermanentActionRuntimeState`) is now the
  **current effective per-turn cap** on both runtime-state structs (`FNumberedActionRuntimeState`
  gained it). Seeded once in `InitialiseActionState` from the config's `MaxUsesPerTurn`; the
  per-turn reset no longer touches it, so a temporary change survives turn boundaries.
- `CanUseAction` (and therefore the Mediator gate and `UTurnBasedAction::CanActivate`) now reads
  the runtime cap, not the config; the config lookup is only "is this action in the loadout".
- New `ATurnBasedPlayerState::GetActionMaxUsesPerTurn(class)` (BlueprintPure) for the UI.
- Removed a null-dereference of `Config->MaxUsesPerTurn` in `ResetActionTurnCounters`.
- Builds clean; not PIE-tested. Field name kept as the owner's `MaxUsesThisTurn` so existing
  Blueprint nodes aren't broken.

## Flags & Follow-ups

- **No modifier API yet** — nothing calls a "set max uses for N turns" function; the state can hold
  the value but only the seed sets it. Needs a server setter plus an expiry that restores the config
  value when it runs out.
- **0 still means unlimited**, so a temporary "action disabled" can't be expressed as a cap of 0
  (use cooldown, a disabled flag, or switch unlimited to -1 when the first modifier is built).
- **Turn-end interaction:** a leaf needing more uses than a lowered cap is unreachable; manual end
  is the stopgap. Planned safeguard: evaluate a leaf against `min(RequiredUsesThisTurn, effective
  cap)` for capped actions (needs the tree's lookup to return the cap too).
- The header comment on `HasActionConfig` still mentions the legacy Actions array (stale).
