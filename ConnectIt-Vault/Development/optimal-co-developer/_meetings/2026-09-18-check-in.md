# 2026-09-18 — Check-in

## Overview

A long, technically dense check-in. Board Shift's mechanics and visuals are confirmed
working end to end (pieces now move with their shifted tiles), the `ActionTag` refactor
landed cleanly, and three stale `_tasks/active.md` rows closed out (`DefaultLevelConfig`,

way. Priorities re-sequenced to bugs first, then the new system as its own white-box
checkpoint (three playtest loadouts, doubling as this week's committed outreach for
multiplayer-testing help), then blocker pieces after that.

## 2. Moving the turn-end fields to the node — this is the real fix

You're right, and it's worse than "a mismatch can occur" — with the threshold on the action's own config, it's a **single shared value two different contexts are forced to agree on**, which is exactly the same bug class as point 1, just relocated. Your example proves it: if `RequiredUsesPerTurnForAutoEnd` lives on PlacePiece globally, it can only ever be one number — set it to 2 for Group1's sake and Group2 (`Place×1 AND Swap×1`) becomes unsatisfiable forever, because "has PlacePiece met its threshold" now always means "≥2," even inside a group that only wanted 1.

The fix: the threshold isn't a property of the action, it's a property of *this leaf, in this tree*. Move it there:

```cpp
USTRUCT()
struct FTurnEndRequirementNode
{
    UPROPERTY(EditAnywhere)
    FGameplayTag ActionTag;                    // leaf if ChildGroups is empty

    UPROPERTY(EditAnywhere, meta=(EditCondition="ChildGroups.Num()==0", ClampMin=1))
    int32 RequiredUsesThisTurn = 1;             // only meaningful on a leaf

    UPROPERTY(EditAnywhere)
    TArray<FTurnEndRequirementNode> ChildGroups; // composite if non-empty

    UPROPERTY(EditAnywhere)
    ETurnEndCombineMode Mode = ETurnEndCombineMode::Any;
};
```

Re-running your exact scenario against this: both leaves read the *same* underlying `UsesThisTurn` runtime counter for PlacePiece, but each leaf applies its own threshold independently. Place once + swap once → Group1's leaf (needs 2) fails, but Group2's two leaves (needs 1 each) both pass → Group2 satisfied → root `Any` fires. Place twice, no swap → Group1's leaf (needs 2) passes on its own → root fires regardless of Group2. Both your groups are independently reachable now.

An action simply absent from the whole tree already doesn't contribute — the flag would be pure redundancy unless you want a fast way to disable one specific leaf without deleting/restructuring it. Drop it, or keep it for that authoring convenience?

One thing that *doesn't* need the same split: `FActionRuntimeState`'s `MatchUsesRemaining` is still conditionally-unread for permanent actions, but that's a dead-and-harmless field, not a mismatched-value bug — nothing behavioral depends on two contexts agreeing on it. I'd leave runtime state as one struct.
