SEPT 2, 2026

Grid tiles and pieces no longer register themselves with the grid world subsystem. This responsibility
should lie with the piece and tile registries we will interface with both the grid subsystem and the actor pool subsystem.
Grid subsystem should be renamed to GridHoverSubsytem. The responsibility of the subsystem is to simply
relay when a tile or a piece THAT IS REGISTERED WITH IT, NOT ALL TILES OR PIECES BECAUSE OF THE ACTOR POOL
are hovered over and to broadcast this. This will help create a generic high level flow for piece creation, pooling and game tracking.

Registries are responsible for tracking real actors to grid positions as well initializing actors
when needed by using the pool and referencing values from the BoardState. The initialization because it 
could potentially deal with BP classes should be Blueprint Implementable.
Registeries should be converted to UObjects instead of ActorComponents to support polymorphism and BP creation.
Each registry will be different for each project but provide the same useful high level functionality.

BoardManager should be renamed to GameBoard or GameBoardVisualizer to better explain it's purpose 
which is to read the valid data board state and create the concrete visual board in the world.
Because of this distinction BoardState should probably live on the GameState (like the turn manager) rather than the BoardManager. 
It is relatively light weight so replication should not be an issue.
We can create in interface for concrete implementations to grab required information without having to cast.

Instead of the player controller reaching into the game board to process a request. We should have something
listening to the player controller broadcasting a ProcessRequest delegate with the same payload.
We could even have the game mode handle this potentially (unless we want swappable logic for each request for testing...)

How are we communicating to the TurnManager that all visual updates are completed and that the next players turn can start?
