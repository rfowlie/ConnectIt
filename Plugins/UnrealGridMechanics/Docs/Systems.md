# UnrealGridMechanics — Systems & Conventions

[README.md](README.md) is the exhaustive per-class reference — every class, its base, its purpose, its key API. This document is the other half: a narrative walkthrough of how the plugin's systems fit together, and the conventions actually in use across them, for anyone orienting themselves before extending the plugin. Read this first; use README.md to look up a specific class once you know which system it belongs to.

## Systems Overview

### Grid Math & Direction (top-level `Public/`)
The foundation everything else builds on. `FGridPosition` is a plain `(X, Y)` integer coordinate with a full operator set (`+`, `-`, `+=`, `-`, `*`, `/`, `==`, `<`) and a custom `GetTypeHash`, so it drops straight into `TMap`/`TSet` keys. `EGridDirection` is the 8-way compass enum, with its own wraparound arithmetic — but note the actual operator set is `+` (two overloads), `-`, and `-=`; there's no `operator+=` despite the symmetric look of the other three (see Known Rough Edges). `UGridMechanics_GridLibrary` layers direction↔rotation conversion, neighbor traversal, and the plugin's N-in-a-row connection analysis (`CountValidWindows`, `CountPossibleGridConnections`, `GetPotentialConnectionCountPerDirection`, `CreateConnectionsFloodMap`) on top of these primitives — this is the reusable scoring engine a consuming project's win-condition logic can call into without reimplementing "how many possible 4-in-a-rows pass through this cell." `UGridMechanics_ShapeLibrary` is a smaller, separate line/shape-detection toolkit (`GetLongestLine(s)`, `GetLinesOfLength`, `IsSquare`) — related in spirit but not layered on top of the connection-analysis functions above it; the two libraries don't call into each other.

### Tiles & Pieces (`Tile/`, `Piece/`)
`AGridTileBase` and `AGridPieceBase` are minimal actor bases — a tile only broadcasts a cursor-over event (`OnGridTileBeginCursorOver`); a piece only knows its own `FGridPosition` and broadcasts its own cursor-over event (`OnGridPieceBeginCursorOver`). Neither self-registers with any subsystem. Nothing here knows about game rules. `UGridTileRegistryComponent` owns the authoritative tile list: on `BeginPlay` it discovers every `AGridTileBase` in the world (plus any spawned later, via an actor-spawned handler), registers each with `UGridHoverSubsystem` so hover can be relayed, and computes row/column/position↔world conversions and board-dimension queries (`GetMinRow`/`GetMaxRow`/`GetRowCount`/etc.) from their actual positions, so a board's dimensions are never hardcoded anywhere. `UGridPieceRegistryComponent` owns live pieces end-to-end: pool retrieve/release, `UGridHoverSubsystem` register/unregister, and a `GetPiece(Position)` lookup backed by its own position map. `AGridUnitBase` is a separate, GAS-enabled piece variant (`AGridPieceBase` + `IAbilitySystemInterface`, owns a `UAbilitySystemComponent`) that still registers itself with `UGridTrackerSubsystem` on `BeginPlay` — a different path from every other actor in this system, and one that's currently a dead end (see Known Rough Edges).

### Board State (`Board/`)
`UBoardStateComponentBase` is a replicated (`SetIsReplicatedByDefault(true)`) `UActorComponent` that owns nothing about *what* the state means — it's an intentionally generic container (`FTileData`: faction owner, multiplier, active flag) plus a broadcast point (`OnBoardStateChanged`) and an interpreter registry (`RegisterInterpreter`). The actual mechanism is explicit-injection observer, not auto-discovery: a `UBoardStateInterpreter` doesn't find its board component on its own — project wiring code (per its header comment, typically a board actor's `BeginPlay`) calls `BindToBoardStateComponent` on it, which does the delegate binding both ways (unbinding from whatever it was previously bound to first). From then on, every time the state-owning subclass writes new state and calls the protected `BroadcastChange()`, every bound interpreter's `OnBoardStateChanged(Component)` fires, and the interpreter casts `Component` to its own project-specific subclass to actually read the typed snapshot — this plugin's base classes never know what that concrete type is. The replication side is left entirely to the subclass: `UBoardStateComponentBase` fires `OnBoardStateChanged` immediately on the server when `BroadcastChange()` is called, and expects a subclass's own `OnRep` to fire the equivalent notification on clients — this plugin only defines the broadcast contract, not the replicated property or its `OnRep`. `UBoardStateComponentBase` itself carries a TODO marking it as transitional: intended to eventually move into a consuming game module and be renamed, since none of its `FTileData` fields are meaningfully generic once a real game's rules are applied to them. `IBoardStateInterface` sits beside this system as a parallel, unrelated observer contract (`BindObserver`/`UnbindObserver`) — nothing in the plugin or its consumer implements it; see Known Rough Edges.

### Board Shifting (`Board/Shift/`)
A compute/animate split, deliberately: `UGridMechanics_GridShiftLibrary::ComputeShiftResult` is pure, synchronous math — given the positions in one row or column and an `FShiftOperation` (axis, index, amount, direction), it returns an `FShiftResult` (the full old-position→new-position remap plus which positions wrapped around the edge). Nothing about this call touches an actor, a tile, or a world. `UBoardShiftComponent` is the actor-driven layer on top: `ComputeShift` just forwards to the library (documented as the call a caller needs an authoritative result from *before* committing any board state), while `PlayShiftAnimation` is presentation-only — it builds per-tile `FTileShiftInstruction`s from an already-computed `FShiftResult`, sends `IGridShiftInterface::PrepareShift` to every affected tile, then ticks `ShiftAlpha` from 0 to 1 over `ShiftDuration` seconds, broadcasting `ApplyShiftAlpha` each tick and `OnShiftComplete` at the end. The tile side of that contract, `IGridShiftInterface`, is what lets a project's own tile Blueprint or C++ class define what "animate to this position" actually looks like without `UBoardShiftComponent` needing to know. This whole actor-driven half of the system is currently vestigial in the current consuming project: its own project-specific shift component absorbed compute, state-mutation, and animation into one class (per that class's own doc comment, because the generic `UBoardShiftComponent` indirection "only ever had one consumer") — but it still calls directly into `UGridMechanics_GridShiftLibrary` and implements `IGridShiftInterface` on its tiles, so the pure-math layer and the interface contract are both still very much live; only the plugin's own actor-driven component sits unused.

### Tile Selection (`Tile/Selector/`)
Two competing shapes for the same idea — "something outside the tile needs to know when it's been selected" — with an explicit deprecation pointing from the newer to the older. `UGridTileSelectorComponent` is the simple original: one `UActorComponent`, one `DECLARE_DYNAMIC_MULTICAST_DELEGATE_TwoParams` (`GridTileSelectorDelegate`), bind to it directly. `IGridTileSelector` supersedes it with a dual-access native interface: a Blueprint-friendly path (`SelectGridTileRegister`/`SelectGridTileUnregister`, taking a dynamic `FGridTileSelectorDelegate`) alongside a C++-friendly path (`BindOnGridTileSelected`/`UnbindOnGridTileSelected`/`GetOnGridTileSelectedDelegate`, working directly against a non-dynamic `FGridTileSelectorMulticastDelegate`) — the header's own doc comment spells out which callers should use which half. The interface's `GetGridTileSelectorComponent()` accessor is explicitly marked `DeprecatedFunction` with a `DeprecationMessage` pointing back at `GetOnGridTileSelectedDelegate()`, which is the live pointer from old pattern to new. In the current consuming project this migration is already essentially complete at the one call site that matters (its tile-selection game-state class calls `IGridTileSelector::Execute_SelectGridTileRegister`/`Execute_SelectGridTileUnregister` directly; the equivalent `UGridTileSelectorComponent`-based calls are present only as commented-out code in the same file) — the interface pattern isn't just the intended direction, it's the one actually wired up.

### Cursor & Hover Tracking (`Cursor/`, `Subsystem/`)
`UGridHoverSubsystem` is a pure hover relay: the registry components register their tiles/pieces with it, it chains each registered actor's own `OnGrid{Tile,Piece}BeginCursorOver` delegate into a single `OnGrid{Tile,Piece}HoverChanged` broadcast, so anything that wants to react to hover state has exactly one place to bind. It relays only for registered actors — never all actors of a type — because pieces come from an object pool. `AGridCursorManagerBase` is built directly on `OnGridTileHoverChanged`: it binds on `BeginPlay`, unbinds on `EndPlay`, and calls a `BlueprintNativeEvent` `UpdateCursor(Tile)` whenever the hovered tile changes — but only while not paused/disabled, a check the base class owns so subclasses don't have to. `AGridCursorSimpleBase` is the one concrete implementation, moving a `UStaticMeshComponent` to the hovered tile's location plus a configurable height offset. `UGridTrackerSubsystem` is a second, structurally similar per-world registry that predates or duplicates the hover-tracking job — own tile list, own hover-start/stop delegates, even its own (fully commented-out) "Unit hover" section. In practice it's reachable from exactly one place: `AGridUnitBase::BeginPlay` calls `RegisterGridUnit` on it. Since `AGridUnitBase` itself isn't used by the current consuming project (which uses the simpler `AGridPieceBase` instead), `UGridTrackerSubsystem` ends up with no live producer in the current project at all — see Known Rough Edges.

### Grid Interfaces (`Interface/`)
A small family of narrow, single-purpose native interfaces that let generic plugin code (or another plugin, like `UnrealTurnBasedMechanics`) query a tile or piece without knowing its concrete class: `IGridFactionInterface` (faction tag/id get/set), `IGridLevelInterface` (a generic stack-height get/set/increment/decrement, useful for e.g. piece-stacking rules), `IGridPieceHandler` (has/get/set/remove piece, implemented by tile-side classes), `IGridTileHandler` (a single `GetGridPosition()` accessor), and `IGridShiftInterface` (the shift-animation contract described above). Unlike `IBoardStateInterface`, these are all genuinely implemented by the current consuming project's own grid piece/tile subclasses — they're the actual seam between this plugin's generic actors and a project's game-specific ones.

### Editor Validation (`UnrealGridMechanicsEditor`)
A single `UGridValidatorBase : UEditorValidatorBase` hooks into Unreal's asset-validation pipeline for world assets (`CanValidateAsset_Implementation` checks `InAsset->IsA<UWorld>()`), intended to find the level's board actor, then check every tile's `GridPosition` against where `UGridTileRegistryComponent`'s world-to-grid math says it should be. It's currently non-functional — see Known Rough Edges — and there's a second, independent instance of essentially the same broken check inside the runtime module itself (`UGridTileRegistryComponent::ValidateTileAlignment()`, editor-only, called from `BeginPlay` under `WITH_EDITOR`), also non-functional for the same underlying reason.

## Conventions

- **Type prefixes**: standard `A`/`U`/`I`/`F`/`E` throughout, no plugin-specific sub-convention layered on top (contrast `UnrealGameMechanics`'s `UDWidget_<TrackedClassName>` debug-widget convention — this plugin has no debug-widget family). Shared top-level enums/structs live in `GridMechanicsBaseEnums.h`/`GridMechanicsBaseStructs.h` — the `Base` infix distinguishes them from any future per-folder enum/struct file, mirroring `UnrealGameMechanics`'s `UnrealGameMechanicsEnums.h`/`UnrealGameMechanicsStructs.h` pattern but without that plugin's own bare naming.
- **Delegates are almost exclusively dynamic** (`DECLARE_DYNAMIC_MULTICAST_DELEGATE*`) — every broadcast-style event in the plugin (`FOnBoardStateChanged`, `FOnShiftStarted`/`FOnShiftCompleted`, `FGridHoverSubsystemTileDelegate`, `FGridHoverSubsystemPieceDelegate`, `FGridTrackerTileDelegate`, `FGridTileComponentDelegate`, `FGridTileBaseBeginCursorOver`) uses this form. The one deliberate exception is `Tile/Selector/GridTileSelector.h`, which pairs a Blueprint-friendly `DECLARE_DYNAMIC_DELEGATE_TwoParams(FGridTileSelectorDelegate, ...)` (single-cast) with a C++-friendly `DECLARE_MULTICAST_DELEGATE_TwoParams(FGridTileSelectorMulticastDelegate, ...)` (native, non-dynamic) for the same conceptual "tile selected" event — the header's own doc comment explains the intended caller for each half. This is the only dual dynamic+native delegate pairing anywhere in the plugin.
- **No `_Internal`-wrapper pattern exists here at all** — every `BlueprintNativeEvent` in the plugin (`AGridCursorManagerBase::UpdateCursor`, `UBoardStateInterpreter::OnBoardStateChanged`, every method on every `Interface/` contract, `AGridTileBase::SendGameplayTag`) is exposed directly with its `_Implementation` override, with no protected wrapper method doing bookkeeping around it the way `UnrealGameMechanics`'s `UGameMechanicsStateBase::Enter()`/`Exit()` wrap their `_Internal` events. Consistent across the whole plugin — nothing to reconcile here, unlike the sibling plugin's unresolved split.
- **`Category` strings are genuinely inconsistent** — verbatim examples actually in the source: `"Grid Mechanics | Library | Direction"` (pipe with spaces, three levels deep), `"Grid|Shift"` / `"Grid|Registry"` (pipe, no spaces), `"Grid|Tile Selector|Register"` (pipe, no spaces, three levels, but a spaced sub-term), `"Grid Mechanics|Cursor"` (spaced on one side of the pipe, not the other), `"Grid | Level"` (pipe *with* spaces, two levels), `"Turn Based | Grid"` (naming residue — this Category string on `UGridTrackerSubsystem`'s delegates references "Turn Based," a concept this plugin explicitly says it has no notion of), `"Board State"` / `"Interpreter"` / `"Grid Faction"` / `"Grid Mechanics"` / `"Grid Tile"` (plain space-separated words, no delimiter). No canonical style has won out; pick whichever feels closest to a neighboring class in the same subfolder rather than inventing a fourth style.
- **Folder/file organization**: one subfolder per system under both `Public/` and `Private/` with matching names (`Board/`, `Board/Interpreter/`, `Board/Shift/`, `Cursor/`, `Interface/`, `Piece/`, `Piece/Unit/`, `Subsystem/`, `Tile/`, `Tile/Selector/`), one class per header/cpp pair, an interface always in its own file. The one deviation: `Board/Shift/BoardShiftComponent.h` includes its sibling `GridShiftTypes.h` via a full `"UnrealGridMechanics/Public/Board/Shift/GridShiftTypes.h"` path rather than the relative `#include "GridShiftTypes.h"` every other cross-reference in the plugin uses.
- **Editor-only code is consistently `#if WITH_EDITOR`-gated**, not split into a separate always-compiled function — `UGridTileRegistryComponent::ValidateTileAlignment()` is declared and defined entirely inside a `WITH_EDITOR` block rather than being unconditionally compiled and only conditionally called.
- **Comment density is high and consistent across the plugin**, unlike the bimodal old/new split documented in `UnrealGameMechanics`'s Systems.md — nearly every non-trivial function across `Board/`, `Board/Shift/`, `Tile/`, and `Subsystem/` carries a rationale comment (e.g. `UBoardStateComponentBase`'s comments spelling out exactly when to call `BroadcastChange()` versus rely on `OnRep`, or `UBoardShiftComponent::ComputeShift`'s comment explaining exactly which caller needs its result before committing state). The `Interface/` contracts are the sparse exception — most carry only the generated `/** * */` stub, consistent with how thin their actual contracts are.

## Known Rough Edges

This plugin doesn't have its own cross-cutting duplication/issues file the way the consuming project does — these are noted here rather than starting a second file for one plugin's internal findings. Each also has a pointer from the relevant row in [README.md](README.md)'s class tables.

- **`IBoardStateInterface`** ([README.md](README.md#board)) — unused/orphaned. Nothing in the plugin or its current consumer implements `BindObserver`/`UnbindObserver`, and its forward declaration (`class FOnBoardStateChanged;`) is dead weight — `FOnBoardStateChanged` is a delegate macro type, not a forward-declarable class, so the declaration compiles but resolves nothing.
- **`UGridTrackerSubsystem` vs `UGridHoverSubsystem`** ([README.md](README.md#subsystem)) — both track hovered tiles. `UGridHoverSubsystem` is the one with live producers: the registry components register tiles/pieces with it, and `AGridCursorManagerBase` / `UTurnBasedAction` bind to its hover delegates. `UGridTrackerSubsystem` is reachable only via `AGridUnitBase::BeginPlay` — and `AGridUnitBase` itself isn't used by the current consuming project (which built its own piece class on the simpler `AGridPieceBase` instead). `AGridTileBase::BeginPlay` still has a commented-out `UGridTrackerSubsystem::RegisterGridTile` call — leftover from an earlier design where tiles self-registered. Net effect: `UGridTrackerSubsystem` currently has no live producer in the current project at all, not just less usage than its sibling.
- **`UBoardShiftComponent`** ([README.md](README.md#board)) — likely unused by the current consumer, which absorbed compute/state-mutation/animation into its own single project-specific component (explicitly noting, in that class's own doc comment, that the generic version "only ever had one consumer" so the extra indirection wasn't earning its keep). The pure-math library and the tile-side interface it depends on (`UGridMechanics_GridShiftLibrary`, `IGridShiftInterface`) are still both live — only this one actor-driven wrapper component is orphaned.
- **`AGridTileBase` vs `UGridTileComponent`** ([README.md](README.md#tile)) — `UGridTileComponent`'s own header comment states "anything that is a grid tile will be required to have this component," but `AGridTileBase` independently declares its own `OnGridTileBeginCursorOver` delegate rather than exposing `UGridTileComponent`'s. No code was found wiring the two together; the intended relationship between them is unclear from the source alone.
- **`IGridTileSelector` vs `UGridTileSelectorComponent`** ([README.md](README.md#tile)) — deprecation-in-progress pairing. Unlike some other "marked deprecated but still the only implementation" cases, this migration is largely done at its one real call site: the current consuming project's tile-selection game-state class uses the interface's `Execute_SelectGridTileRegister`/`Execute_SelectGridTileUnregister` live, with the equivalent `UGridTileSelectorComponent`-based calls present only as commented-out code in the same file.
- **`UGridValidatorBase`'s non-functional `BoardActor` loop** ([README.md](README.md#module-unrealgridmechanicseditor)) — `GridValidatorBase.cpp:26`'s `for (TActorIterator<AActor> It(World); It; ++It) { }` has an empty body, so `BoardActor` is never assigned and the validator always falls through to `NotValidated`. Its own TODO gives the history: it used to identify the board actor via an `IGridBoardManagerInterface` that has since been removed from the codebase entirely (its only implementer, the consuming project's board manager, had no generic plugin-side purpose) — the validator needs a new way to find the board actor before its actual alignment check can run at all.
- **`UGridTileRegistryComponent::ValidateTileAlignment()`'s body is entirely commented out** ([README.md](README.md#tile)) — a second, independent non-functional validation check, blocked on the same root cause as the editor validator above: its own inline TODO notes it depends on tile actors being given a `GridPosition` in-editor, which isn't currently happening, so the check would otherwise report every tile as misaligned.
- **`EGridDirection`'s operator set** ([README.md](README.md#base-types-top-level-public)) — `+` (two overloads), `-`, and `-=` exist; there is no `operator+=`, despite the visual symmetry with `-=` suggesting one should exist.
- **`UBoardStateInterpreter`'s "Chimera Framework" naming residue** ([README.md](README.md#board)) — its header comment ("Lives in Chimera Framework -- no project-specific type knowledge") and `ClassGroup=(Chimera)` both name a predecessor project this code was ported from; described generically here rather than treated as this plugin's own naming convention. See the project-level [naming conventions notes](../../../Source/ConnectIt/Docs/Conventions.md#discrepancies) for the equivalent project-level flag.
- **`UnrealTurnBasedMechanics.Build.cs`** lists `UnrealGridMechanics` in both `PublicDependencyModuleNames` and `PrivateDependencyModuleNames` — redundant, since the Public listing alone already satisfies private use. Minor, not functionally harmful.
