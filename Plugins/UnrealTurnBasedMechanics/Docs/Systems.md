# UnrealTurnBasedMechanics — Systems & Conventions

[README.md](README.md) is the exhaustive per-class reference — every class, its base, its purpose, its key API. This document is the other half: a narrative walkthrough of how the plugin's systems fit together, and the conventions actually in use across them, for anyone orienting themselves before extending the plugin. Read this first; use README.md to look up a specific class once you know which system it belongs to.

## Systems Overview

### The Action Stack (`Action/`, `Action/Spectator/`)
Every controller's moment-to-moment behaviour is one entry on top of an actual stack (`UTurnBasedActionsComponent::ActionStack`), never a flat "current mode" enum. `UTurnBasedActionBase` is the root: `Activate`/`ForceDeactivate` plus `Activate_Internal`/`Deactivate_Internal`/`ForceDeactivate_Internal`/`PostInitialiseAction` BlueprintNativeEvent hooks a concrete action overrides. Two branches specialise it:

- **`UTurnBasedAction`** — the per-turn, player-owned action. It carries cooldown/completion config (`MaxCompletionsPerTurn`, `CooldownTurns`), an Enhanced-Input-driven grid-tile selection pipeline (`OnGridTileHoverChanged` → `IsValidHoverTile`/`HandleValidHover`/`HandleHoverCleared` → `OnSelectionInputTriggered` → `IsValidSelectionTile`/`HandleValidSelection`), and a generic `InputBindings` array (`FInputTagBinding`, from `UnrealGameMechanics`) so a designer can add a new bound input as pure data — no new C++. Binding itself is delegated to a per-instance `UInputTagBinder` (also `UnrealGameMechanics`), built fresh in `InitialiseAction` and bound/unbound by `BindInput`/`UnbindInput` around activation.
- **`UTurnBasedSpectatorAction`** — the non-turn-owning branch: idle, spectator, and pause views. Never completes naturally, carries no cooldown tracking, and is torn down the same way it's built up (`Deactivate()` is just `ForceDeactivate()` under a clearer name). `UTurnBasedPauseAction` is the one concrete framework-provided instance — spawns/removes a configurable `PauseWidgetClass` and disables/enables controller input.

`UTurnBasedActionsComponent` owns the stack and five designer-assigned system-action slots vended from a `UActionLoadoutDataAsset`: **root** (sits at the bottom during your own turn, mandatory), **idle** (pushed the instant your turn ends, active through the `Updating` phase while resolution plays), **spectator** (pushed for the duration of an opponent's turn), **pause** (pushed on top during system pause, stack preserved underneath), and **awaiting-confirmation** (pushed while a board-change request this participant just sent is in flight — see below). `PushAction` force-deactivates the current top without popping it, then activates the new top; `SafePopAction` refuses to pop the last remaining entry so the stack can never go empty mid-match; `ClearAndPush` tears down everything and installs a new sole entry — the shape every `Notify*` turn-lifecycle method (`NotifyTurnStarted`, `NotifyOpponentTurnStarted`, `NotifyTurnEnded`, `NotifyMatchEnded`) ultimately calls.

**Board-change confirmation.** When a `UTurnBasedAction` calls `RequestBoardChange`, it broadcasts `OnChangeRequested`, which the actions component's `HandleBoardChangeRequested` catches: it sets `bAwaitingRequestConfirmation = true`, pushes the awaiting-confirmation action (if one is configured), and re-broadcasts as `OnBoardChangeRequested` for project-specific glue (a player controller, typically) to route to the server. While that flag is true, `PushAction`/`SafePopAction`/`TryPushActionByRef`/`ClearAndPush` all refuse to run — the stack is frozen until the answer comes back. The *only* thing project glue needs to call once the server responds is `NotifyBoardChangeOutcome(Request, bSucceeded)`: on success it force-completes the action that made the request; on failure it simply reactivates it so the player can retry. Neither this component nor the plugin needs to know *why* a request succeeded or failed, only that it did — this is this plugin's own instance of the project-level [Server-Authoritative Action Request workflow](../../../Source/ConnectIt/Docs/Workflows/ServerAuthoritative-ActionRequest.md), with `FTurnActionRequest` as the tagged envelope.

### Controller / GameMode / GameState / PlayerState Scaffolding (`Framework/`)
`APlayerController` and `AAIController` are sibling branches of the engine's controller hierarchy — neither can inherit shared turn-based wiring from the other. Rather than duplicate that wiring, `ATurnBasedPlayerControllerBase` and `ATurnBasedAIController` each own the same three components (`UTurnBasedParticipantComponent`, `UTurnBasedActionsComponent`, `UTurnBasedControllerCoordinatorComponent`), and **`UTurnBasedControllerCoordinatorComponent` is the mediator** that actually wires the other two together identically on both branches. On `BeginPlay` it resolves both sibling components, then:

- **Participant → Actions**: `OnTurnNotificationReceived` (carries an `FTurnNotification` with `ETurnPhase`) is translated into `NotifyTurnStarted`/`NotifyTurnEnded` calls on the actions component depending on phase; `OnOpponentTurnStarted` (slot index only) is resolved against the manager's already-replicated `Participants`/`TurnNumber` to build an `FTurnStartContext` and calls `NotifyOpponentTurnStarted`.
- **Actions → Participant**: `OnTurnEndRequested` calls the participant component's `ServerSubmitTurnEnd` RPC.
- **GameState → Actions** (optional, `bRouteMatchPhaseChanges`): `ATurnBasedGameState::OnMatchPhaseChanged` is translated into `NotifyPaused`/`NotifyUnpaused`/`NotifyMatchEnded` calls, tracking a local `bIsPaused` flag since `EMatchPhase::InProgress` fires both at the start of every turn *and* on unpause and the coordinator needs to tell those apart.

Neither the participant component nor the actions component knows the other exists — the coordinator is the only class that does. `ATurnBasedPlayerControllerBase` additionally implements `IGridFactionInterface` (from `UnrealGridMechanics`) for `GetFactionId`, returning the participant component's slot index — the one point where this plugin hands the grid layer a faction identity to key off. `ATurnBasedGameMode` holds match config (`TurnDuration`, `ForfeitThreshold`, `ReconnectTimeout`) and pushes it into the manager component on `HandleMatchHasStarted`; `ATurnBasedGameState` and `ATurnBasedPlayerState` are both thin, replicated-state-only classes with manager-only setters gated by `friend class UTurnBasedParticipantManagerComponent` — nothing else is meant to mutate `MatchPhase`, `SlotIndex`, `TurnsMissed`, `bForfeited`, or `bIsReady` directly.

### Turn Order (`Turn/Order/`)
A one-method-family strategy pattern: `ITurnOrderInterface` declares `GetNextParticipantIndex`, `GetFirstParticipantIndex`, and `GetStrategyName`, all `BlueprintNativeEvent` so a project can implement a whole new ordering scheme in Blueprint with zero C++. `USequentialTurnOrderStrategy` (the default, assigned automatically in the manager's `BeginPlay` if nothing is configured) walks forward from the current index looking for the next connected, non-forfeited participant; `URandomTurnOrderStrategy` is the same contract with random selection. The manager component never hardcodes ordering logic itself — it only ever calls through `TScriptInterface<ITurnOrderInterface> TurnOrderStrategy`, so a new strategy is purely additive.

### Turn/Participant — the Match State Machine (`Turn/Participant/`)
Two components split "am I the one whose turn it is" from "what is the match's overall state right now":

- **`UTurnBasedParticipantComponent`** lives on each controller. It exposes the client-safe `IsMyTurn()` flag (set only by `ClientReceiveTurnNotification`/`ClientReceiveOpponentTurnStarted`, **never valid on the server** — server code must check `UTurnBasedParticipantManagerComponent::IsActiveParticipant` instead) and two server RPCs, `ServerNotifyReady`/`ServerSubmitTurnEnd`, that forward straight to the manager.
- **`UTurnBasedParticipantManagerComponent`** lives on `ATurnBasedGameState` and is the actual state machine: replicated `CurrentPhase`, `ActiveParticipantIndex`, `TurnNumber`, and `Participants` (an `FTurnParticipantInfo` array). Its phase graph runs `WaitingForParticipants` → `WaitingForReady` (`BeginReadyCheck`, advanced by `CheckReadyStatus` once every registered participant's `PlayerState->IsReady()` is true) → `TurnStart`/`TurnActive` (`StartTurn`, which also arms a `TurnTimerHandle` from `TurnDuration`) → `TurnEnd` → (gated) → back to `TurnStart` for the next participant, or `GameOver` once `CheckGameOver` finds one or fewer active participants left.

**Turn timeout, forfeit, and reconnect** are all handled here too: `HandleTurnTimeout` increments the active participant's `TurnsMissed` and forfeits them once `ForfeitThreshold` is reached, then ends the turn as `TimedOut`. `NotifyParticipantDisconnected` (called from `ATurnBasedGameMode::Logout`) pauses the match (`ETurnPhase::TurnPaused` / `EMatchPhase::Paused`) and arms a `ReconnectTimerHandle`; `NotifyParticipantReconnected` clears that timer and resumes exactly where the turn left off, replaying the current turn's notification to the reconnected participant. If the reconnect timer expires first, `HandleReconnectTimeout` ends the turn as `TimedOut` the same way a normal timeout would.

**Turn-end is gated by a gameplay tag, not a hold counter.** This is the piece of this plugin most likely to have changed since you last read about it. `EndTurn` does not advance the match itself — it sets `EMatchPhase::Updating` (so every client suspends input while resolution visuals play), then calls `QueueTagContainer(FGameplayTagContainer(TurnEndEventTag))` on `UnrealGameMechanics`' `UGameEventTaskSubsystem`. `AdvanceToNextParticipant` (the function that actually asks the turn-order strategy for the next index and calls `StartTurn`) is registered in `BeginPlay` as that tag's completion handler via `BindOnTagComplete` — it only runs once every task any system in the project has registered against `TurnEndEventTag` has genuinely finished, exactly the same phase-barrier guarantee `UGameEventTaskManager` gives any other gated tag. If `TurnEndEventTag` is left unset, `EndTurn` calls `AdvanceToNextParticipant` immediately instead and `BeginPlay` logs an error — there's no silent no-op path. This plugin has no opinion on what the tag is named or who registers against it; that's entirely project configuration. It also means turn-end is not a special case in this codebase at all — it's one more instance of the same "Gated Event Sequencing via Tags" pattern used everywhere else `UGameEventTaskSubsystem` shows up (see the project-level [workflow doc](../../../Source/ConnectIt/Docs/Workflows/GameplayTag-EventSequencing.md)). An earlier `BeginResolutionHold`/`EndResolutionHold` counter API filled this same role and does not exist in current source — see Known Rough Edges.

### Debug Widgets (`Debug/`)
Both debug widgets subclass `UDWidgetBase` (`UnrealGameMechanics`) and follow its `BindDelegates`/`UnbindDelegates`/`RefreshFields` contract. `UDWidget_TurnBasedActionsComponent` is explicitly per-controller (not a GameState singleton), resolving `ResolvedSource` via `GetOwningPlayer()->FindComponentByClass<UTurnBasedActionsComponent>()` — correct, since the actions component genuinely lives on the controller. It caches `ActionTag` only for the top and root actions, never the live action pointer — those objects expose `BlueprintCallable` `Complete()`/`Cancel()`, so nothing reachable from the widget's cached fields can accidentally mutate live game state — and it also caches `IsAwaitingRequestConfirmation()`, giving a debug view direct visibility into the board-change-confirmation guard described above. `UDWidget_TurnBasedParticipantManagerComponent` binds five delegates (`OnTurnPhaseChanged`, `OnActiveControllerChanged`, `OnParticipantForfeited`, `OnAllParticipantsReady`, `OnGameOver`), each just calling `RefreshAll()` — but see Known Rough Edges for a likely bug in how it resolves its source in the first place.

## Conventions

- **Type prefixes**: standard `U`/`I`/`F`/`E`/`A` throughout — this is the one plugin in the suite with `A`-prefixed classes (`ATurnBasedGameMode`, `ATurnBasedGameState`, `ATurnBasedPlayerState`, `ATurnBasedAIController`, `ATurnBasedPlayerControllerBase`), since match/controller scaffolding is inherently actor-based here in a way the other plugins' generic mechanics aren't.
- **Dual dynamic + native delegate declaration, genuinely consistent this time.** Nearly every event in this plugin is declared twice: once `DECLARE_DYNAMIC_MULTICAST_DELEGATE*` (`BlueprintAssignable`, for Blueprint/replication-safe binding) and once `DECLARE_MULTICAST_DELEGATE*` with an `_Native` suffix (for C++-only, lambda-friendly, no-reflection-overhead binding) — e.g. `FOnActionBaseEvent`/`FOnActionBaseEvent_Native`, `FOnTurnEndRequested`/`FOnTurnEndRequested_Native`, `FOnBoardChangeRequested`/`FOnBoardChangeRequested_Native`, `FOnMatchPhaseChanged`/`FOnMatchPhaseChanged_Native`. `TurnBasedMechanicsDelegates.h` documents *why* two of its delegates (`FOnTurnNotification_Native`, `FOnOpponentTurnStarted_Native`) have no dynamic counterpart at all: a commented-out block is kept in place with the note "DYNAMIC delegates cannot be declared like this, they do not compile properly" — `const FTurnNotification&`-by-reference dynamic multicast delegates don't compile, so those two exist only in native form. This dual-declaration convention is deliberate and, per this plugin's own README, arguably the pattern the rest of the suite should adopt — `UnrealGameMechanics`, for comparison, declares every delegate dynamic-only.
- **`_Internal`-suffixed `BlueprintNativeEvent` wrapper, applied consistently.** `UTurnBasedActionBase` exposes plain non-event `Activate()`/`ForceDeactivate()` methods that do bookkeeping (setting `bIsActive`, firing delegates) and then call protected `Activate_Internal`/`Deactivate_Internal`/`ForceDeactivate_Internal` `BlueprintNativeEvent`s as the actual override point. Every concrete action subclass follows this same wrapper shape rather than exposing `BlueprintNativeEvent`s directly — contrast `UnrealGameMechanics`, where the equivalent split (`GameMechanicsStateBase` vs. `GameMechanicsStateSimple`) is unresolved and inconsistent within that plugin itself.
- **Dense rationale comments are the house style, not the exception.** Nearly every non-trivial method across this plugin carries a comment explaining *why*, not just what — e.g. `TurnNumber`'s doc comment on why it needs its own `ReplicatedUsing` rather than piggybacking on `CurrentPhase`'s; the `AdvanceToNextParticipant` `UFUNCTION()` comment explaining exactly why its unused `FGameplayTag` parameter still has to match `OnManagerComplete`'s signature; the `HandleBoardChangeRequested` comment explaining why its "already awaiting a request" branch should be unreachable but is kept as defense-in-depth anyway. This plugin's own README calls it out as the reference model for comment style across the rest of the plugin suite.
- **`Category` strings are consistently pipe-delimited with a `Turn Based|` prefix.** Verbatim examples actually in the source: `"Turn Based|Actions"`, `"Turn Based|Behaviour"`, `"Turn Based|Config"`, `"Turn Based|Components"`, `"Turn Based|Coordinator"`, `"Turn Based|Strategy"`, `"Turn Based|Notifications"`, `"Turn Based|Debug"`, `"Action|Config"`, `"Action|Delegates"`, `"Action|Selection"`, `"Action|Input"`, `"Action|Cooldown"`, `"Loadout"`, `"Loadout|System Actions"`, `"Loadout|Turn Actions"`. This is meaningfully more disciplined than the pipe-spacing/casing free-for-all documented in `UnrealGameMechanics`' own Conventions section — worth treating as the model to match when adding a new `UFUNCTION`/`UPROPERTY` here or elsewhere in the suite.
- **Folder/file organization**: one subfolder per system under both `Public/` and `Private/` with matching names (`Action/`, `Action/Spectator/`, `Framework/Controller/`, `Framework/GameMode/`, `Framework/GameState/`, `Framework/PlayerState/`, `Turn/Order/`, `Turn/Participant/`, `Debug/`); one class per header/cpp pair; shared top-level delegates/enums/library/structs live in their own `TurnBasedMechanics*.h` files rather than inside a system's own folder. Cross-references `#include` relative to `Public/` (e.g. `#include "Action/TurnBasedAction.h"`, `#include "Turn/Order/TurnOrderInterface.h"`).

## Known Rough Edges

This plugin doesn't have its own cross-cutting duplication/issues file the way the consuming project does — these are noted here rather than starting a second file for one plugin's internal findings. Each also has a pointer from the relevant row in [README.md](README.md)'s class tables or Known Discrepancies section.

- **The resolution-hold mechanism has changed since this plugin was last documented, and the change is easy to miss.** `UTurnBasedParticipantManagerComponent` no longer has `BeginResolutionHold`/`EndResolutionHold` at all — turn-end advancement is now gated by a designer-set `TurnEndEventTag` through `UnrealGameMechanics`' `UGameEventTaskSubsystem` (`QueueTagContainer`/`BindOnTagComplete`), described in full under Systems Overview above. The hold-counter API itself had already replaced a still-earlier fixed-duration `TurnResolutionDuration` timer, so this is the *second* mechanism this specific piece of behaviour has moved through. The project-level Resolution Hold Counter workflow doc this plugin's README previously linked has been removed from the project's Workflows folder entirely (superseded by the [Gated Event Sequencing via Tags workflow](../../../Source/ConnectIt/Docs/Workflows/GameplayTag-EventSequencing.md)) — if you find any other doc, comment, or diagram anywhere still describing a resolution-hold *counter*, it's describing a retired mechanism, not this one. See [README.md](README.md#turnparticipant) (the `UTurnBasedParticipantManagerComponent` row) and its Known Discrepancies entry.
- **`UTurnBasedActionsComponent::CloneActionsFromLoadout`** casts its owning `AController*` to `APlayerController*` to resolve an `UEnhancedInputLocalPlayerSubsystem`, with a self-acknowledged TODO immediately above the cast (`TurnBasedActionsComponent.cpp:74`, "don't love this cast — do we need to be using AController instead of PlayerController; will AI controller even need an actions component?"). Harmless today since the cast fails safe to `nullptr` for AI controllers, but it's an open design question about whether `ActionsComponent` should exist on `ATurnBasedAIController` at all. See [README.md](README.md#action) (the `UTurnBasedActionsComponent` row).
- **Redundant Public+Private dependency listing.** `UnrealTurnBasedMechanics.Build.cs` lists both `UnrealGridMechanics` and `UnrealGameMechanics` in `PublicDependencyModuleNames` *and* `PrivateDependencyModuleNames` — the Public listing alone already satisfies any private use, so the Private entries are inert duplication. Confirmed still present in current source; not functionally harmful, just noise. See [README.md](README.md#key-dependencies).
- **Dual dynamic/native delegate declaration is deliberate here, but the rest of the plugin suite hasn't adopted it.** `UnrealGameMechanics` declares every delegate dynamic-only; this plugin's own README suggests the dual-declaration pattern documented above is arguably the one other plugins should move toward, not the other way around. See [README.md](README.md#notable-design-patterns).
- **`UDWidget_TurnBasedParticipantManagerComponent::BindDelegates` likely can never resolve its source.** It calls `GetOwningPlayer()->FindComponentByClass<UTurnBasedParticipantManagerComponent>()` — but `UTurnBasedParticipantManagerComponent` is created as a subobject of `ATurnBasedGameState` (see `ATurnBasedGameState`'s constructor), not of the player controller. `AActor::FindComponentByClass` only searches the calling actor's own components, so calling it on the owning `APlayerController` should return `nullptr` every time, leaving `ResolvedSource` unset, `bSourceValid` permanently false, and the widget's five delegate binds skipped entirely. Not previously documented anywhere; worth confirming against a running instance and, if confirmed, changing the lookup to resolve through the world's `AGameStateBase` instead (the same pattern `UTurnBasedParticipantComponent::GetParticipantManager()` already uses).
- Two small stale/half-finished spots, no functional impact: `TurnBasedMechanicsStructs.h` opens with a `// TurnBasedTypes.h` header comment left over from before the file was renamed; `ATurnBasedGameMode.h` and `UTurnBasedParticipantManagerComponent.cpp`'s `BroadcastControllerChanged` both carry open `// TODO` questions (a commented-out `SwapPlayerControllers` override, and "where and why do we need this?" on a function whose body is the TODO itself).
